## Bối cảnh

CI hiện đang **xanh hơn thực tế**. Bốn chỗ đang bỏ lọt lỗi:

1. `mypy app || true` — dấu `|| true` nuốt mọi lỗi kiểu. Cổng này chưa bao giờ chặn được gì.
2. CI chỉ quét `tests/unit`, `tests/integration`, `tests/api` ⇒ file `backend/tests/test_app_boots_standalone.py` nằm ở thư mục `tests/` gốc **chưa từng chạy một lần nào**.
3. **19 test chatbot tự bỏ qua trên CI** với lý do `Chưa có chunk nào — chạy scripts/reindex_kb.py --all trước`. CI không có bước nạp kho tài liệu, nên toàn bộ F4 (chatbot RAG) chưa từng được kiểm chứng.
4. Không có `uv.lock`. CI giải phụ thuộc lại từ đầu mỗi lần ⇒ một thư viện lên phiên bản mới là CI đỏ dù không ai đụng vào code.

## Việc cần làm

**a. Bỏ `|| true` khỏi bước type check**

```yaml
      - name: Type check
        run: mypy app          # bỏ "|| true"
```

Nếu `mypy` báo lỗi có sẵn, đừng sửa code người khác — thêm `# type: ignore[<mã-lỗi>]` kèm chú thích ngắn, hoặc liệt kê module vào `[[tool.mypy.overrides]]` trong `pyproject.toml` và nhắn nhóm.

**b. Thêm bước nạp và index kho tài liệu, đặt NGAY SAU bước `Run migrations`**

```yaml
      - name: Seed dữ liệu và index kho tài liệu
        run: |
          python scripts/seed.py
          python scripts/seed_kb.py
          python scripts/reindex_kb.py --all
```

**c. Đổi đường quét test** — hai bước pytest hiện tại gộp lại còn:

```yaml
      - name: Unit tests
        run: pytest tests/unit -v --cov=app --cov-report=

      - name: Integration and API tests
        run: >-
          pytest tests/integration tests/api tests/test_app_boots_standalone.py -v
          --cov=app --cov-append --cov-report=term-missing
          --cov-fail-under=80
```

**d. Sinh và commit `uv.lock`**

```bash
cd backend && uv lock
git add uv.lock
```

Rồi đổi bước cài đặt trong `ci.yml`:

```yaml
      - name: Install dependencies
        run: uv sync --frozen --all-groups
```

## API có sẵn (đã chạy, xem Swagger tại `/docs`)

| Method | Path | Dùng để |
|---|---|---|
| `GET` | `/kb/articles?q=&categoryId=&tag=&status=&page=&pageSize=` | Danh sách + tìm kiếm |
| `GET` | `/kb/articles/{slug}` | Xem chi tiết |
| `POST` | `/kb/articles` | Tạo bài mới |
| `PATCH` | `/kb/articles/{id}` | Sửa bài |
| `POST` | `/kb/articles/{id}/publish` | Đăng bài |
| `POST` | `/kb/articles/{id}/unpublish` | Gỡ bài |
| `GET` | `/kb/categories` | Danh sách chủ đề |

Hình dạng dữ liệu trả về (`ArticleListItem`):

```ts
{ id, slug, title, summary, status, category, tags,
  viewCount, publishedAt, updatedAt, version }
```

Bài chi tiết có thêm `contentMd` (Markdown) và `author`.

> ⚠️ **Tham số `status` chỉ Admin dùng được — vai trò khác luôn chỉ thấy bài `PUBLISHED`.** Đăng nhập bằng tài khoản `IT_AGENT` sẽ không thấy bài nháp của mình, và đó là **đúng theo thiết kế**, không phải lỗi. Đừng mất thời gian đi tìm. Bộ lọc trạng thái trên giao diện chỉ nên hiện với `ADMIN`.

## Test 1 — Quét toàn bộ route

Ý tưởng: duyệt mọi route trong `app.routes`, gọi thử **không kèm token**, và khẳng định server trả 401 hoặc 403 — tuyệt đối không phải 200.

```python
CONG_KHAI = {
    "/health",
    "/api/v1/auth/login",
    "/api/v1/auth/register",
    "/api/v1/auth/refresh",
    "/docs", "/openapi.json", "/redoc",
}

def test_moi_endpoint_deu_doi_xac_thuc(client):
    """Endpoint mới quên Depends(get_current_user) sẽ bị bắt ở đây.

    Danh sách trắng phải viết TAY. Nếu ai đó thêm endpoint công khai mới,
    họ buộc phải sửa file này — và lúc sửa sẽ phải tự hỏi 'endpoint này
    công khai có đúng không?'. Đó chính là tác dụng của test.
    """
    for route in app.routes:
        duong_dan = getattr(route, "path", None)
        if duong_dan is None or duong_dan in CONG_KHAI:
            continue
        for method in sorted(getattr(route, "methods", set()) - {"HEAD", "OPTIONS"}):
            # Thay tham số đường dẫn bằng một UUID hợp lệ bất kỳ
            url = re.sub(r"\{[^}]+\}", str(uuid4()), duong_dan)
            r = client.request(method, url)
            assert r.status_code in (401, 403), (
                f"{method} {duong_dan} tra {r.status_code} khi KHONG co token"
            )
```

## Bối cảnh

Cột `chat_messages.no_context_found` đã được ghi đúng từ ngày đầu, nhưng **chưa ai đọc nó**. Mỗi lần chatbot trả lời "tôi không tìm thấy tài liệu phù hợp", hệ thống đang lặng lẽ ghi lại một chỗ thiếu tài liệu — và không ai nhìn.

Báo cáo này khép vòng lặp cải thiện chatbot: **câu hỏi không trả lời được → biết thiếu tài liệu gì → viết bài → chatbot trả lời được**. Không có nó thì việc bổ sung tài liệu chỉ là đoán.

Vòng lặp đó chạy đúng qua hai feature bạn phụ trách trong docx — F7 (báo cáo) sinh ra tín hiệu, F5 (kho tài liệu) tiêu thụ nó. Nên đây là task nằm gọn trong lane của bạn, không phải việc mượn của ai.

## Việc cần làm

**a. Endpoint mới**

```
GET /reports/unanswered-questions?from=&to=&page=&pageSize=
```

Quyền: `ADMIN` **và** `IT_AGENT` (giống `/reports/ai-accuracy` — Agent chính là người viết tài liệu).

**b. Truy vấn**

Lấy các `chat_messages` có `role = 'USER'` mà **tin nhắn ngay sau đó** của trợ lý có `no_context_found = true`. Dùng `LEAD(...) OVER (PARTITION BY session_id ORDER BY created_at)` — xem `dashboard.py::_pause_seconds_subquery()` đã dùng đúng kỹ thuật này.

## Bối cảnh

Task nhỏ nhất trong ngày — hợp để lấy lại đà.

`AuthService.change_password` hiện như sau (`service.py:214`):

```python
def change_password(self, user: User, current_password: str, new_password: str) -> int:
    if not verify_password(current_password, user.password_hash):
        raise InvalidCredentialsError("Mật khẩu hiện tại không đúng")   # ← trả 401
```

Hai vấn đề:

**Sai mã lỗi.** `InvalidCredentialsError` → **401**, nghĩa là "bạn chưa đăng nhập". Nhưng người gọi API này **đã đăng nhập rồi** — token của họ hợp lệ, chỉ mật khẩu cũ gõ sai. Đúng ra phải là **403**.

Đây không phải chuyện câu chữ: frontend thường cài sẵn interceptor "gặp 401 thì xoá token và đá về trang đăng nhập". Nghĩa là **gõ nhầm mật khẩu cũ một lần là bị đăng xuất**, và người dùng không hiểu vì sao.

Sửa hôm nay là đúng lúc: trang Đổi mật khẩu (US-01/US-05 UI) nằm trong danh sách chưa giao ở cuối file. Backend đúng mã lỗi trước thì lúc ai đó dựng trang, họ chỉ phải xử lý một trường hợp thay vì hai.

**Không ghi vết thất bại.** Hàm này có `logger.info` khi đổi **thành công**, nhưng khi **thất bại** thì im lặng. Đó mới là sự kiện đáng ghi: nhiều lần thất bại liên tiếp trên một tài khoản là dấu hiệu có người đang dò mật khẩu.

## Việc cần làm

**a. Đổi ngoại lệ**

```python
from app.core.exceptions import ForbiddenError

if not verify_password(current_password, user.password_hash):
    logger.warning(
        "doi mat khau that bai: sai mat khau hien tai",
        extra={"extra_fields": {"user_id": str(user.id), "email": user.email}},
    )
    raise ForbiddenError("Mật khẩu hiện tại không đúng")
```

> ⚠️ **Tuyệt đối không ghi mật khẩu — cũ hay mới — vào log**, kể cả một phần. Log được gom về nơi lưu trữ tập trung và nhiều người đọc được.

**b. Sửa test cũ**

Trong `tests/api/test_auth.py` có test đang khẳng định `401`. Nó **phải được sửa thành `403`**, không phải xoá đi.

**c. Thêm hai test**

1. Sai mật khẩu hiện tại → **403**, và mã lỗi trong body là `FORBIDDEN`
2. Sai mật khẩu hiện tại → token đang dùng **vẫn còn hiệu lực** (gọi `GET /users/me` ngay sau đó vẫn 200)

Test thứ hai chính là bằng chứng cho vấn đề đã nêu ở trên.
