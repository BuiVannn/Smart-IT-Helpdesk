### Việc cần làm

Viết các Pydantic schema cho module quản lý người dùng. Đây là "hợp đồng" giữa frontend và backend — quy định API nhận gì và trả gì.

Cần 6 class:

| Class | Dùng khi | Các field |
|---|---|---|
| `UserCreate` | Admin tạo user | email, password, fullName, role, departmentId |
| `UserUpdate` | Admin sửa user | tất cả optional: fullName, phone, role, departmentId, isActive |
| `UserProfileUpdate` | User tự sửa hồ sơ | fullName, phone, avatarUrl (**không có role** — không cho tự đổi vai trò) |
| `UserResponse` | Trả về một user | id, email, fullName, role, department, isActive, createdAt |
| `UserListFilter` | Lọc danh sách | role, departmentId, isActive, q |
| `DepartmentResponse` | Trả về phòng ban | id, code, name |

### Code khởi đầu

```python
"""Schema cho module quản lý người dùng."""

from datetime import datetime
from uuid import UUID

from pydantic import BaseModel, ConfigDict, EmailStr, Field

from app.modules.users.constants import UserRole


class StrictModel(BaseModel):
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)


class ResponseModel(BaseModel):
    model_config = ConfigDict(from_attributes=True, populate_by_name=True)


class UserCreate(StrictModel):
    email: EmailStr
    password: str = Field(min_length=8, max_length=128)
    full_name: str = Field(min_length=2, max_length=150, alias="fullName")
    role: UserRole = UserRole.EMPLOYEE
    department_id: UUID | None = Field(default=None, alias="departmentId")


class DepartmentResponse(ResponseModel):
    id: UUID
    code: str
    name: str


class UserResponse(ResponseModel):
    id: UUID
    email: str
    full_name: str = Field(serialization_alias="fullName")
    role: UserRole
    department: DepartmentResponse | None = None
    is_active: bool = Field(serialization_alias="isActive")
    created_at: datetime = Field(serialization_alias="createdAt")


# TODO: viết tiếp UserUpdate, UserProfileUpdate, UserListFilter
```

### Lưu ý

- ⚠️ **`UserResponse` TUYỆT ĐỐI KHÔNG được có field `password_hash`.** Đây là lỗi bảo mật nghiêm trọng nhất có thể mắc ở file này.
- Field vào dùng `alias` (frontend gửi `fullName`), field ra dùng `serialization_alias`.
- `UserProfileUpdate` **không có** `role` và `isActive` — nếu có, nhân viên tự đổi mình thành Admin được.

### Code khởi đầu

```python
"""Schema cho module ticket."""

from datetime import datetime
from uuid import UUID

from pydantic import BaseModel, ConfigDict, Field

from app.modules.tickets.constants import AiStatus, TicketPriority, TicketStatus


class StrictModel(BaseModel):
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)


class ResponseModel(BaseModel):
    model_config = ConfigDict(from_attributes=True, populate_by_name=True)


class TicketCreate(StrictModel):
    title: str = Field(min_length=5, max_length=200)
    description: str = Field(min_length=10, max_length=5000)
    category_id: UUID | None = Field(default=None, alias="categoryId")
    priority: TicketPriority | None = None
    # KHÔNG có requester_id ở đây — server lấy từ token đăng nhập (quy tắc BR-01)


class UserBrief(ResponseModel):
    id: UUID
    full_name: str = Field(serialization_alias="fullName")


class CategoryBrief(ResponseModel):
    id: UUID
    slug: str
    name: str


class TicketResponse(ResponseModel):
    id: UUID
    code: str
    title: str
    description: str
    status: TicketStatus
    priority: TicketPriority
    ai_status: AiStatus = Field(serialization_alias="aiStatus")
    requester: UserBrief
    assignee: UserBrief | None = None
    category: CategoryBrief | None = None
    sla_resolution_due_at: datetime | None = Field(
        default=None, serialization_alias="slaResolutionDueAt"
    )
    created_at: datetime = Field(serialization_alias="createdAt")
    version: int


# TODO: viết tiếp TicketUpdate, TicketStatusChange, TicketAssign, TicketFilter
```

### Lưu ý

- ⚠️ **`TicketCreate` KHÔNG được có `requesterId`.** Server luôn lấy người tạo từ token — nếu nhận từ client, ai cũng tạo ticket giả danh người khác được.
- `TicketStatusChange` phải có `version` — dùng cho optimistic lock, chống hai người sửa cùng lúc.
- `TicketFilter` có `status` là **list** (`list[TicketStatus] | None`) vì frontend gửi `?status=NEW&status=ASSIGNED`.

```python
def list_stale_for_index(self) -> list[KbArticle]:
    stmt = select(KbArticle).where(
        KbArticle.status == ArticleStatus.PUBLISHED,
        (KbArticle.indexed_at.is_(None)) | (KbArticle.indexed_at < KbArticle.updated_at),
    )
    return list(self.session.execute(stmt).scalars().all())
```


### Gợi ý cho hai chỗ dễ sai

**Sắp xếp phải có tie-breaker:**
```python
stmt.order_by(Notification.created_at.desc(), Notification.id.desc())
```
> `created_at` do `transaction_timestamp()` sinh, nên nhiều thông báo ghi trong **cùng một transaction** (giao việc + đổi trạng thái) có mốc thời gian **giống hệt nhau**. Thiếu `id.desc()`, hai trang liên tiếp có thể trả trùng bản ghi hoặc bỏ sót — lỗi chỉ lộ ra khi dữ liệu đủ nhiều, tức là lúc demo.

**`mark_read` phải lọc theo `user_id`:**
```python
update(Notification)
    .where(Notification.user_id == user_id)      # ← thiếu dòng này là lỗ hổng
    .where(Notification.id.in_(ids))
```
> Không có điều kiện `user_id`, ai gửi lên id bất kỳ cũng đánh dấu đã đọc thông báo của người khác.

### Lưu ý

- ⚠️ **`UnreadCountResponse` chỉ được có đúng một con số.** Endpoint này frontend gọi **30 giây một lần cho mọi người đang online** — mọi field thêm vào đây đều nhân với số người dùng nhân với tần suất polling (ADR-0008).
- `NotificationResponse` **không trả đường dẫn dựng sẵn**, chỉ trả `entityType` + `entityId` để frontend tự dựng URL. Backend không nên biết cấu trúc route của frontend: khi frontend đổi route, mọi thông báo cũ trong DB sẽ trỏ sai.
- **Không `commit()`** trong repository — mở/đóng transaction là việc của service.

```yaml
      - name: Lint
        run: ruff check . && black --check .

      - name: Kiểm tra kiểu
        run: mypy app || true      # tạm cho phép fail, siết lại sau

      - name: Kiểm tra ranh giới module

      - name: Unit test
```

### Code khởi đầu — `StatusBadge.tsx`

```tsx
import { cn } from '@/lib/utils'
import type { TicketStatus } from '@/types'

const STATUS_CONFIG: Record<TicketStatus, { label: string; className: string }> = {
  NEW:               { label: 'Mới',              className: 'bg-slate-100 text-slate-700' },
  ASSIGNED:          { label: 'Đã giao',          className: 'bg-blue-100 text-blue-700' },
  IN_PROGRESS:       { label: 'Đang xử lý',       className: 'bg-amber-100 text-amber-800' },
  PENDING_REQUESTER: { label: 'Chờ phản hồi',     className: 'bg-purple-100 text-purple-700' },
  RESOLVED:          { label: 'Đã xử lý',         className: 'bg-emerald-100 text-emerald-700' },
  CLOSED:            { label: 'Đã đóng',          className: 'bg-slate-200 text-slate-600' },
  CANCELLED:         { label: 'Đã huỷ',           className: 'bg-slate-100 text-slate-500' },
}

export function StatusBadge({ status, className }: { status: TicketStatus; className?: string }) {
  const config = STATUS_CONFIG[status]
  return (
    <span
      className={cn(
        'inline-flex items-center rounded-full px-2.5 py-0.5 text-xs font-medium',
        config.className,
        className,
      )}
    >
      {config.label}
    </span>
  )
}
```

### Hai component còn lại

**`PriorityBadge.tsx`** — 4 mức: `LOW` Thấp (xám) · `MEDIUM` Bình thường (xanh dương) · `HIGH` Cao (cam) · `URGENT` Khẩn cấp (đỏ). Làm tương tự `StatusBadge`.

**`SlaBadge.tsx`** — khó hơn một chút, nhận `dueAt: string | null` và `resolvedAt: string | null`, tự tính trạng thái:

```tsx
import { timeUntil } from '@/lib/utils'   // hàm này đã có sẵn

// Logic:
```
